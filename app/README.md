# Клієнтська частина системи підтримки ухвалення рішень щодо B2B-замовлень

Веб-застосунок для менеджера B2B-продажів: замість «сухого» списку замовлень він бачить
**прогноз імовірності успішного закриття** кожного замовлення, **фактори**, які на прогноз
вплинули, і може **перерахувати прогноз** після зміни даних. Аналітик додатково бачить метрики
якості моделі та важливість ознак, адміністратор - керує ролями користувачів.

Бекенду в проєкті немає: усі дані надходять із mock-API на MSW. Це свідома межа проєкту
(див. розділ 10 технічного завдання) - прогноз є детермінованою імітацією на демонстраційних
даних, а не роботою реальної ML-моделі.

---

## 1. Запуск з нуля

Потрібен Node.js 20 або новіший.

```bash
cd app
npm install          # або npm ci, якщо є package-lock.json
npm run dev          # http://localhost:5173
```

Відкрийте `http://localhost:5173` - застосунок перекине на екран входу.

Інші команди:

| Команда | Що робить |
|---|---|
| `npm run dev` | сервер розробки з гарячим перезавантаженням |
| `npm run build` | перевірка типів (`tsc -b`) і збірка в `dist/` |
| `npm run preview` | локальний перегляд зібраної версії |
| `npm run lint` | ESLint (typescript-eslint), має бути 0 зауважень |
| `npm run lint:fix` | те саме з автовиправленням |
| `npm run format` | форматування Prettier |
| `npm test` | Vitest з покриттям (`vitest run --coverage`) |
| `npm run test:watch` | тести у режимі спостереження |

Якщо `npm run preview` показує білу сторінку - перевірте, що файл
`dist/mockServiceWorker.js` існує: його копіює `npx msw init public/ --save`,
і без нього mock-API не запуститься.

## 2. Ролі та демо-доступи

| Роль | Що бачить |
|---|---|
| **Менеджер** | власні замовлення (список + картка), перерахунок прогнозу |
| **Аналітик** | усе те саме + розділ «Аналітика» (KPI моделі, важливість ознак, тренд) |
| **Адміністратор** | усе те саме + розділ «Користувачі» (зміна ролей) |

Облікові дані для входу (їх також видно на екрані авторизації - кнопка «Заповнити»):

| Роль | Email | Пароль |
|---|---|---|
| Менеджер | `manager@demo.ua` | `manager123` |
| Аналітик | `analyst@demo.ua` | `analyst123` |
| Адміністратор | `admin@demo.ua` | `admin123` |

Демонстраційні дані: 8 користувачів, 12 клієнтів і 72 замовлення з фіксованим seed, тому
набір даних однаковий на будь-якій машині. Менеджер `manager@demo.ua` бачить 24 власні
замовлення, аналітик і адміністратор - усі 72.

Повідомлення про невдалий вхід **однакове** і для неіснуючого користувача, і для
неправильного пароля - щоб за текстом помилки не можна було підбирати облікові дані.
На клієнті підсвічуються лише ті помилки, які справді перевірені на клієнті (порожнє поле,
формат email, короткий пароль).

## 3. Як перемкнути стани інтерфейсу

У правому нижньому куті є кнопка **«Режим перевірки»**. Вона відкриває панель, якою можна
відтворити кожен стан без правок коду. Вибір зберігається в `localStorage`
(ключ `stem-forecast:check-mode`) і діє на всі екрани одразу.

| Поле панелі | Що робить |
|---|---|
| Список замовлень | `Реальні дані` / `Порожній результат` / `Помилка запиту` |
| Картка замовлення | те саме для `GET /orders/:id` |
| Аналітика | те саме для `GET /analytics/model` |
| Користувачі | те саме для `GET /users` |
| Перерахунок прогнозу | `Успішний перерахунок` / `Помилка перерахунку` |
| Затримка відповіді, мс | штучна затримка mock-API (щоб побачити скелетони) |
| Імітувати відсутність мережі | запити завершуються помилкою мережі |
| Скинути | повертає типові значення |

### П'ять обов'язкових станів даних (ТЗ, п. 4)

1. **loading** - скелетон фіксованої висоти (не порожній екран). Побачити його легко:
   поставте затримку 1500-3000 мс і перезавантажте розділ.
2. **success** - дані.
3. **empty** - «Порожній результат» у панелі, або фільтр, що нічого не знаходить
   (наприклад, статус «Втрачено» й клієнт, у якого таких замовлень немає). Показує
   пояснення й пораду, а не порожню таблицю.
4. **error** - «Помилка запиту» у панелі; на екрані з'являється кнопка **«Повторити»**.
5. **offline/деградація** - банер «дані можуть бути застарілими». Щоб побачити:
   спершу завантажте список, потім увімкніть «Імітувати відсутність мережі» і змініть
   будь-який фільтр - старі дані лишаться на екрані, але зверху з'явиться банер.

### Шість станів кнопки «Перерахувати прогноз» (Рисунок 2)

| Стан | Як відтворити |
|---|---|
| idle | відкрити картку замовлення |
| hover | навести курсор |
| active | натиснути й утримувати кнопку |
| loading | натиснути кнопку (у стані loading вона блокує повторні натискання) |
| success | дочекатися відповіді - підтвердження зникає через 2 секунди |
| error | вибрати «Помилка перерахунку» в панелі й натиснути кнопку |

## 4. Маршрути

| Маршрут | Екран | Кому доступний |
|---|---|---|
| `/login` | вхід | усім |
| `/orders` | список замовлень | авторизованим |
| `/orders/:id` | картка замовлення | авторизованим (менеджер - лише власні) |
| `/analytics` | аналітика | аналітик, адміністратор |
| `/admin/users` | користувачі | адміністратор |

Фільтри, сортування й сторінка списку зберігаються в query-параметрах
(`?dateFrom=…&status=…&sortBy=…&page=2`), тому посиланням можна поділитися, а
перезавантаження сторінки не втрачає вибірку.

## 5. Тести

```bash
npm test
```

Три рівні тестів (усього 230 перевірок у 18 файлах):

- **unit** (`tests/unit/`) - форматери (`format`), розрахунок рівня ризику (`risk`), побудова
  й розбір query-параметрів (`queryParams`), фільтрація/сортування/пагінація (`orderQuery`),
  логіка прогнозу (`forecast`), прапорці режиму перевірки (`checkMode`), клієнт API
  (`apiClient`), валідація форми входу (`validation`), контракти mock-API (`mocks`),
  побудова й екранування CSV (`csv`), обхід сторінок під час експорту (`ordersApi`);
- **component** (`tests/component/`) - `OrderTable` у чотирьох станах, `RecalculateButton`
  (усі шість станів + заборона подвійного натискання), `Filters` (застосування й скидання),
  `LoginPage` (валідація та однакова відмова), `CheckModePanel`;
- **integration** (`tests/integration/`) - потік «логін → список → картка → перерахунок» на
  MSW, стани панелі списку, збереження фільтрів в URL, доступ за ролями.

Поріг покриття модулів логіки - **80 %** (`src/lib`, `src/api`, `src/mocks`). Поріг
налаштований у `vite.config.ts` і ламає збірку, якщо його не досягнуто; фактичні показники -
понад 96 % тверджень і понад 90 % гілок.

## 6. Технології

- React 19 + Vite + TypeScript у строгому режимі;
- React Router 7 - маршрутизація, захист маршрутів роллю;
- TanStack Query 5 - запити, кеш, повторні спроби, збереження даних під час оновлення;
- MSW 2 - mock-API із затримками та керованими помилками (прапорці в `localStorage`);
- Recharts - графіки важливості ознак і тренду метрик;
- CSS Modules + змінні дизайн-токенів (`src/styles/tokens.css`), жодного CSS-фреймворку;
- Vitest + React Testing Library + `@testing-library/user-event`;
- ESLint (`typescript-eslint`) + Prettier.

## 8. Домовленості та свідомі рішення

- **Токен доступу живе лише в пам'яті модуля** (`src/api/token.ts`), у `localStorage` його
  немає. Тому після перезавантаження сторінки сесія завершується - це вимога захищеності,
  а не дефект.
- **Жодного `dangerouslySetInnerHTML`**: весь вивід екранується React.
- **Адаптивність 360 / 768 / 1280 px**: до 767 px список рендериться картками, від 768 px -
  таблицею. Горизонтального скролу сторінки немає.
- **Доступність**: семантичні теги, `aria-live` для повідомлень, `aria-busy` під час
  завантаження, `aria-sort` у заголовках таблиці, видимий фокус, навігація з клавіатури,
  посилання «Перейти до основного вмісту»; вимоги враховано за WCAG 2.2.
- **Графіки завантажуються на вимогу**: сторінки «Аналітика» й «Користувачі» винесені в
  окремі чанки, тому початковий бандл не тягне Recharts.
- **Експорт вибірки**: кнопка «Експорт CSV» на списку вивантажує **всю** вибірку з
  урахуванням фільтрів (функція `fetchAllOrders` обходить сторінки поспіль), файл має BOM,
  тому Excel коректно відкриває кирилицю. На картці замовлення є кнопка «Копіювати
  посилання» - адреса сторінки картки замовлення копіюється в буфер обміну; якщо браузер
  не дає доступу до буфера, застосунок показує підказку скопіювати адресу вручну.

## 9. Обмеження проєкту

- реального бекенду й ML-моделі немає: прогноз - детермінована імітація на демонстраційних
  даних;
- автентифікація імітована на MSW, справжнього сервера авторизації немає;
- мобільних застосунків, SSR і хмарного деплою не передбачено - застосунок запускається
  локально.
