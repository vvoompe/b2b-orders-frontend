# Розділ 2. Програмна реалізація

Розділ охоплює опис інструментів, архітектури та прийомів реалізації клієнтської
частини системи підтримки ухвалення рішень щодо B2B-замовлень, а також посилання на
програмний код у Git.

---

## 2.1. Інструменти та бібліотеки

| Інструмент | Версія | Для чого обрано |
|---|---|---|
| React [4] | 19 | компонентна модель, найпоширеніша бібліотека для SPA, велика екосистема |
| Vite [5] | 8 | швидкий dev-сервер і збірка, мінімальна конфігурація |
| TypeScript [6] | 6 (strict) | типізація контрактів даних, помилки видно до запуску |
| React Router [7] | 7 | маршрутизація, захищені маршрути за роллю |
| TanStack Query [8] | 5 | керування серверним станом: кеш, повторні спроби, стани запиту без ручного коду |
| MSW (Mock Service Worker) [9] | 2 | mock-API на рівні мережі: реальні HTTP-запити перехоплюються, код застосунку не знає про імітацію |
| Recharts [10] | 3 | декларативні графіки (важливість ознак, тренд метрики) |
| CSS Modules + змінні | - | локальні стилі без глобальних конфліктів, дизайн-токени, медіазапити |
| Vitest [11] + React Testing Library [12] | 5 / 16 | тести поведінки користувача, а не внутрішньої реалізації |
| ESLint + Prettier | - | єдиний стиль, відсутність типових помилок |

Версії наведено відповідно до встановлених залежностей у файлі `package-lock.json`.

**Чому не Next.js:** продукт є клієнтським SPA без SSR і без власного бекенду; вимога
«фронтенд як складова програмної системи» виконана без серверного рендерингу, а зайвий
серверний шар ускладнив би пояснення меж проєкту. Це рішення зафіксовано в §2.6 (межі).

## 2.2. Архітектура застосунку

Структура коду повторює поділ за предметними областями (features), а не за типами файлів:

```
src/
  api/         клієнт запитів, схеми й типи даних
  mocks/       MSW-обробники та генератор демонстраційних даних
  components/  спільні UI-блоки: стани, таблиця, графіки, банери
  features/    auth, orders, analytics, users - логіка та екрани
  app/         маршрути, провайдери, загальний каркас сторінки
  lib/         форматери, розрахунок рівня ризику, робота з query-параметрами
  styles/      токени й глобальні стилі
```

Потік даних: **екран → хук даних (TanStack Query) → функція запиту → MSW-обробник →
демонстраційні дані**. Завдяки такому поділу заміна mock-API на реальний бекенд не потребує
змін на екранах: достатньо прибрати MSW і змінити базовий URL.

## 2.3. Прийоми реалізації

### 2.3.1. Стани інтерфейсу як окремий компонент
Кожен екран із даними має п'ять станів: завантаження (скелетон фіксованої висоти, щоб
верстка не «стрибала»), успіх, порожній результат, помилка з кнопкою «Повторити» та банер
застарілих даних. Стани виведено в один компонент-обгортку, тому однакова поведінка
гарантована на всіх екранах, а не дублюється.

### 2.3.2. Адаптивність
Три контрольні ширини: 360, 768 і 1280 px. На широкому екрані замовлення показані таблицею,
на вузькому - картками; фільтри переходять із горизонтальної панелі у випадний блок;
графіки зменшують кількість підписів. Перебудова подання спирається на медіазапити CSS [13].
Горизонтальної прокрутки сторінки немає на жодній ширині - це перевірено вручну в
інструментах розробника браузера.

### 2.3.3. Кросбраузерність
Використано стандартні властивості CSS без вендор-специфічних хаков. Перевірка виконана в
браузері на рушії Chromium (Chrome і Edge). Типові розбіжності рушіїв (округлення
flex-елементів, поведінка `gap` у таблицях, зовнішній вигляд системних контролів) описані
в §2.5.

### 2.3.4. Захищеність
- токен доступу зберігається **лише в пам'яті модуля**, не в `localStorage`, тому не
  залишається в постійному сховищі браузера;
- вивід даних виконується засобами React (екранування за замовчуванням), `innerHTML`
  та `dangerouslySetInnerHTML` не використовуються;
- введення перевіряється на клієнті до відправлення (порожні поля, формат e-mail, межі суми);
- повідомлення про невдалий вхід однакове для випадків «користувача не існує» і «невірний
  пароль» - щоб не давати змоги підбирати облікові дані за текстом помилки;
- пароль не потрапляє в логи, у коді немає жодних секретів і ключів.

### 2.3.5. Доступність і зручність користування
Семантичні теги; `aria-live` для повідомлень про результат операцій; `aria-busy` під час
завантаження; `aria-sort` у заголовках таблиці; видимий фокус для клавіатурної навігації;
посилання «Перейти до основного вмісту». Порожні стани містять пояснення й підказку, а не
лише «нічого не знайдено». Вимоги до доступності враховано з настанов WCAG 2.2 [14];
інструментальний аудит контрасту в цій роботі не проводився, тому числових гарантій
контрасту не наводимо.

### 2.3.6. Тестування
Три рівні: модульні тести логіки (форматери, розрахунок рівня ризику, побудова
query-параметрів), компонентні (таблиця у чотирьох станах; кнопка перерахунку - усі стани й
заборона подвійного натискання; панель фільтрів), інтеграційний сценарій
«вхід → список → картка → перерахунок прогнозу» на MSW. Поріг покриття модулів логіки - 80 %.

Покриття вимірюється лише для модулів логіки: `src/lib`, `src/api` і `src/mocks`
(налаштування `coverage.include` у `vite.config.ts`). Компоненти й екрани в цей показник не
входять, тому числа нижче не можна читати як покриття всього застосунку. Фактичний результат
прогону (`npm test`): **18 файлів, 230 тестів, усі пройдено**; покриття модулів логіки -
**96,74 % тверджень, 90,74 % гілок, 98,49 % функцій, 98,01 % рядків**. `npm run lint` - без зауважень,
`npm run build` - без помилок типів. Окремо виконано перевірку в справжньому браузері
(Chromium/Edge): пройдено вхід, список, картка, перерахунок прогнозу, аналітика й розділ
користувачів; помилок у консолі - 0; завантажений CSV-файл перевірено на вміст.

### 2.3.7. Експорт результатів і передача вибірки
Кнопка «Експорт CSV» на списку вивантажує всю вибірку з урахуванням активних фільтрів, а не
лише поточну сторінку: функція `fetchAllOrders` послідовно обходить сторінки. Якщо вибірка
перевищує 50 сторінок, експорт завершується **явною помилкою з проханням звузити фільтри**,
а не обрізаним файлом. Дані передаються в чисту функцію побудови CSV, яка екранує лапки,
коми та переноси рядків за RFC 4180, нейтралізує значення, що починаються із символу формули
(щоб Excel не виконав їх як формулу), і додає BOM, щоб Excel коректно відкривав кирилицю.

На картці замовлення кнопка «Копіювати посилання» кладе в буфер обміну адресу цього екрана.
Якщо браузер не дає доступу до буфера, застосунок не мовчить: показує підказку скопіювати
адресу вручну, а підтвердження оголошується через `aria-live`.

## 2.4. Ключові технічні рішення та їх обґрунтування

1. **Серверний стан через TanStack Query, а не `useEffect`.** Запити з кешем, повторними
   спробами та інвалідацією після перерахунку прогнозу - це типова задача бібліотеки; ручний
   код дав би більше місць для помилок, особливо у стані «дані застаріли».
2. **MSW замість «заглушок у коді».** Імітація живе на рівні мережі, тому екрани працюють із
   реальними HTTP-запитами; при появі справжнього API зміни мінімальні.
3. **Фільтри в URL.** Стан списку можна надіслати колезі посиланням, а кнопка «Назад» працює
   передбачувано - це прямий виграш у зручності, який оцінюється критерієм UX.
4. **Скелетони замість спінера.** Фіксована висота заповнювачів прибирає «стрибок» верстки
   після завантаження - помітна деталь, яку на захисті легко показати в дії.

## 2.5. Відомі обмеження та крайні випадки

- mock-API імітує затримку 400-900 мс і помилки за прапорцем «режим перевірки»; реальна
  мережева деградація не відтворюється;
- прогноз - детермінована імітація на демонстраційних даних, а не ML-модель: це межа проєкту,
  зафіксована в ТЗ (п. 10). З тієї ж причини метрики на екрані «Аналітика» є синтетичними, і
  про це прямо сказано в інтерфейсі;
- при одночасному перерахунку прогнозу й оновленні списку перемагає остання відповідь
  (захист від «перегонів» реалізовано скасуванням попереднього запиту).

## 2.6. Посилання на програмний код (Git)

Код застосунку опубліковано у публічному репозиторії:

**https://github.com/vvoompe/b2b-orders-frontend**

## 2.7. Як запустити

```
git clone https://github.com/vvoompe/b2b-orders-frontend
cd b2b-orders-frontend/app
npm ci
npm run dev        # відкрити http://localhost:5173
npm test           # тести + покриття
npm run build      # production-збірка
```

Демонстраційні облікові дані та опис ролей наведено в README та в керівництві користувача
(Розділ 3).
