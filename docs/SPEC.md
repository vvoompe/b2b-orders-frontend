# ТЗ: клієнтська частина системи підтримки ухвалення рішень щодо B2B-замовлень

**Дисципліна:** «Розробник фронтенду програмних систем» (STEM-проєкт, І. Юрчук)
**Виконавець:** Олександр Маркграф, ІПЗ-31 (підгрупа 1)
**Напрям досліджень кафедри:** № 1 (інтелектуальні системи підтримки рішень) і № 10 (цифрові сервіси для бізнесу)
**Формулювання теми:** Розроблення клієнтської частини системи підтримки ухвалення рішень щодо B2B-замовлень засобами React

---

## 1. Призначення продукту

Веб-застосунок для менеджера B2B-продажів: замість «сухого» списку замовлень він бачить
**прогноз імовірності успішного закриття** кожного замовлення, **фактори**, які на прогноз
вплинули, і може **перерахувати прогноз** після зміни даних. Аналітик додатково бачить
метрики якості моделі та важливість ознак.

Бекенду немає: дані - демонстраційний набір через mock-API (MSW). Це свідома межа проєкту,
вона описана в записці.

## 2. Ролі

| Роль | Що бачить |
|---|---|
| Менеджер | власні замовлення (список + картка), перерахунок прогнозу |
| Аналітик | + розділ «Аналітика» (метрики моделі, важливість ознак) |
| Адміністратор | керування користувачами (окремий екран, спрощено) |

## 3. Екрани та вимоги

| № | Маршрут | Екран | Обов'язкові елементи |
|---|---|---|---|
| 1 | `/login` | Вхід | email + пароль, клієнтська валідація, стан loading, повідомлення про помилку без підказки, яке поле винне |
| 2 | `/orders` | Список замовлень | таблиця на десктопі / картки на мобільному, фільтри (період, клієнт, статус, діапазон суми), сортування за сумою та датою, пагінація, збереження фільтрів в URL |
| 3 | `/orders/:id` | Картка замовлення | реквізити, прогноз (число + ймовірність), перелік факторів, кнопка «Перерахувати прогноз», історія змін прогнозу |
| 4 | `/analytics` | Аналітика | KPI якості моделі, графік важливості ознак, тренд метрики за період |
| 5 | `/admin/users` | Користувачі (адмін) | таблиця користувачів, зміна ролі |

## 4. Обов'язкові стани інтерфейсу (за критеріями оцінювання)

Кожен екран із даними мусить мати **п'ять** станів:
1. **loading** - скелетон, а не порожній екран;
2. **success** - дані;
3. **empty** - запит успішний, але записів немає (з поясненням і порадою, без «порожньої таблиці»);
4. **error** - помилка запиту з кнопкою «Повторити»;
5. **offline/деградація** - банер «дані можуть бути застарілими», якщо запит не пройшов.

Кнопка «Перерахувати прогноз» має **6 станів**: idle, hover, active, loading (блокує повторні
натискання), success (зникає через 2 с), error (з можливістю повторити).

## 5. Технології (зафіксовано)

- React 19 + Vite 8 + TypeScript 6 (strict)
- React Router (маршрутизація), маршрути захищені роллю
- TanStack Query (запити, кеш, retry, stale-state)
- MSW - mock-API з реалістичними затримками та помилками (керовано через localStorage-прапорці)
- Recharts - графіки (важливість ознак, тренд)
- CSS Modules + змінні (дизайн-токени), медіазапити; жодного CSS-фреймворку
- Vitest + React Testing Library + @testing-library/user-event
- ESLint (typescript-eslint) + Prettier, скрипти `lint`, `test`, `build`

## 6. Нефункціональні вимоги

- **Адаптивність:** 360 / 768 / 1280 px; на мобільному таблиця стає картками; жодного
  горизонтального скролу.
- **Кросбраузерність:** перевірено в браузерах на рушії Chromium (Chrome і Edge); CSS без
  вендор-специфічних хаков.
- **Захищеність:** токен тримається в пам'яті модуля (не в localStorage), React екранує
  вивід (жодного `dangerouslySetInnerHTML`), валідація вводу на клієнті, повідомлення про
  невдалий вхід однакове для «нема користувача» і «невірний пароль», пароль не логується.
- **Доступність:** семантичні теги, `aria-*` для станів (aria-busy, aria-live для повідомлень),
  навігація з клавіатури, видимий фокус; вимоги враховано за WCAG 2.2, інструментальний аудит
  контрасту не проводився.
- **UX:** зрозумілі порожні стани, збереження фільтрів в URL, відсутність «стрибків» верстки
  (скелетони фіксованої висоти).

## 7. Тестування (обов'язково, оцінюється критерієм C)

- **unit:** форматери (сума, дата), розрахунок рівня ризику, побудова query-рядка фільтрів;
- **component:** `OrderTable` у станах loading/empty/error/success; `RecalculateButton` -
  усі 6 станів і заборона подвійного натискання; `Filters` - застосування і скидання;
- **integration:** потік «логін → список → картка → перерахунок» на MSW;
- поріг покриття модулів логіки - **≥ 80 %** (`vitest run --coverage`).

## 8. Структура репозиторію

```
app/
  src/
    api/            клієнт mock-API, схеми даних, типи
    mocks/          MSW-обробники, генератор даних
    components/     UI-компоненти (спільні, стани, графіки)
    features/       orders/, auth/, analytics/, users/
    app/            маршрути, провайдери, layout
    lib/            форматери, робота з query-параметрами
    styles/         токени, глобальні стилі
  tests/            тести (unit, component, integration)
  README.md         запуск з нуля
```

- [ ] `npm test` - зелено, покриття логіки ≥80 %;
- [ ] `npm run lint` - 0 помилок;
- [ ] усі п'ять екранів працюють, стани перемикаються прапорцями в панелі «Режим перевірки»;

## 10. Що НЕ входить (межі проєкту)

- власний бекенд і реальна ML-модель (прогноз - детермінована імітація на mock-даних);
- автентифікація з реальним сервером (імітація токена);
- реальна модель прогнозу та справжні метрики якості на екрані «Аналітика» (KPI синтетичні);
- мобільні застосунки, SSR, деплой у хмару (запуск локально, `npm run dev`).
