# ВИСНОВКИ

Метою роботи було розробити клієнтську частину системи підтримки ухвалення рішень щодо
B2B-замовлень засобами React - тобто не просто «список із фільтром», а інструмент, який
пояснює менеджерові, за які замовлення братися першими. Мета досягнута: застосунок
реалізовано, зібрано, протестовано й перевірено в реальному браузері.

**Що зроблено.** Побудовано односторінковий застосунок на React 19 + Vite 8 + TypeScript з
п'ятьма екранами: вхід, список замовлень, картка замовлення з прогнозом і чинниками впливу,
аналітика (метрики якості моделі та важливість ознак) і керування користувачами з поділом за
ролями. Дані надходять із mock-API на MSW, що імітує справжній сервер: затримки відповіді,
помилки 401/403/404/500 і обрив мережі, - тому всі стани інтерфейсу можна відтворити без
змін у коді (панель «Режим перевірки»).

**Кількісні результати.** `npm run build` - без помилок типів; `npm run lint` - без зауважень;
`npm test` - **230 тестів у 18 файлах, усі пройдено**. Покриття вимірюється лише для модулів
логіки (`src/lib`, `src/api`, `src/mocks`) і становить **96,74 % тверджень** та **98,49 %
функцій**; це не покриття всього застосунку. Перевірка у справжньому браузері (Chromium/Edge)
пройшла без жодної помилки в консолі: виконано вхід під демонстраційним адміністратором,
перехід між усіма екранами, перерахунок прогнозу (стан кнопки змінився), копіювання посилання
(вміст буфера обміну перевірено) та експорт CSV (файл завантажено, перевірено BOM, кирилицю й
структуру рядків).

**Ключові технічні рішення.** Серверний стан винесено в TanStack Query, а не в ручні
`useEffect`: кеш, повторні спроби та збереження попередніх даних під час оновлення дали
передбачувану поведінку екранів. Фільтри зберігаються в адресі сторінки, тому вибірку можна
передати посиланням. Токен доступу тримається лише в пам'яті модуля, `dangerouslySetInnerHTML`
не використовується, повідомлення про невдалий вхід однакове для всіх видів відмови - ці
рішення описані в розділі 2 і свідомо обрані на користь захищеності.

**Чого зроблено не було (межі роботи).** Реального бекенду й справжньої ML-моделі в проєкті
немає: прогноз - детермінована імітація на демонстраційних даних, метрики якості моделі на
екрані «Аналітика» синтетичні, автентифікація імітована на MSW. Кросбраузерність заявлена за
стандартними властивостями CSS і перевірена в браузерах на рушії Chromium (Chrome і Edge);
повний набір рушіїв та старих браузерів не тестувався, інструментальний аудит контрасту не
проводився. Мобільні застосунки, серверний рендеринг і хмарне розгортання не передбачені
завданням.

**Що дала робота.** Найціннішим було не написання екранів, а проєктування поведінки: описати
п'ять станів даних і шість станів однієї кнопки, домовитися про контракт із API, розділити
код за предметними областями й довести логіку тестами. Саме тому застосунок поводиться
однаково на всіх екранах, а не «десь скелетон, а десь порожній екран».

**Напрями подальшого розвитку.** Заміна mock-API на справжній бекенд (код екранів при цьому
не змінюється), додавання реальної моделі прогнозу й живлення розділу «Аналітика» справжніми
метриками, збереження вибірок за користувачем, експорт у XLSX із форматуванням та розширення
аналітики порівнянням періодів.
